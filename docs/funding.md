# 無料枠の原資と支援の受け口

無料枠は運営者のAPIキーで動いていて、`worker/wrangler.toml` の `LIMIT_GLOBAL` が1日の費用の上限を決めています。
上限は「1日に出せる額 ÷ 探究1つの平均費用」で決めます（2026-09 時点: $3 ÷ $0.009 ≒ 330。根拠は docs/model-bench-2026-09.md）。
原資が増えればこの上限を上げられる、という構造なので、その受け口を用意しています。

このドキュメントは方針と、その理由の記録です。

## 方針の要約

| 項目 | 決めたこと |
|---|---|
| お金 | GitHub Sponsors と Ko-fi へのリンクだけを置く。アプリと Worker には決済のコードも支援者の記録も持たない |
| 見返り | 一切付けない。支援しても本人の1日の回数は増えない（増えるのは全体の上限） |
| APIキーの提供 | 受け付けない。代わりに「自分のキーで使う」ことを支援の形として案内する |
| 相談 | 既存のご意見フォーム（`/feedback`）に種類「💛 支援について」を足して受ける。新しいエンドポイントは作らない |
| 導線 | 設定の無料枠タブ、全体の上限に達したとき（だけ）、ヘルプの最後、README |

## 決済手段

| | 手数料 | 支援者の手間 | 日本在住の個人で | 採否 |
|---|---|---|---|---|
| GitHub Sponsors | プラットフォーム手数料 0%（決済実費のみ） | GitHub アカウントが要る | Stripe Connect 経由で受け取れる。本人確認と W-8BEN の提出がある | 採用。リポジトリと同じ場所で、開発者に届く |
| Ko-fi | 単発の支援は Ko-fi 側 0%（決済実費のみ） | アカウント不要、カードだけで済む | Stripe / PayPal 経由 | 採用。GitHub を持たない学習者の受け皿 |
| Buy Me a Coffee | 5% + 決済実費 | アカウント不要 | 同上 | 不採用。Ko-fi とほぼ同じ機能で手数料だけ高い |
| Stripe Payment Links | 3.6% | いちばん楽 | 本人確認と特定商取引法の表記が要り、寄付を受ける用途が認められるか事前に確認が要る | 不採用。1日 $3 の規模に対して手続きが重い |
| PayPal.me | — | — | 日本の個人アカウントは国内の個人間の受け取りに制限がある | 不採用 |

どちらも外部サイトへのリンクなので、カード情報はこのアプリにも Worker にも一切届きません。

## 税務上の扱い（要確認）

以下は方針を決めるための整理で、税務の助言ではありません。実際に受け取りが始まったら税務署か税理士に確認してください。

- **見返りのない個人からの支援は贈与**として扱われる前提で設計しています。個人からの贈与には年110万円の基礎控除があり、この規模では通常そこに収まります。
- **見返りを付けると対価（雑所得など）になります。** 「支援すると回数が増える」「名前を載せる」「優先的に使える」などは付けないでください。消費税や特定商取引法の表記、支援額に応じて回数を渡す形なら資金決済法（前払式支払手段）の検討まで必要になりえます。
- アプリの文言も同じ理由で「支援 → 全体の上限が上がる」だけを言い、「支援 → あなたの回数が増える」とは書きません（`src/pages/SupportPage.tsx`）。

## APIキーの提供を受け付けない理由

デポジット済みのAPIキーを「使ってください」と預ける申し出は、受け付けません。

1. **漏れたときの費用を負うのは提供者です。** Worker のシークレット・ログ・運用ミスのどこから漏れても、請求は提供者の口座に行きます。上限の設定されていないキーなら青天井で、運営者が引き受けられる責任ではありません。
2. **出所を確かめられません。** 盗まれたキーかどうか見分ける手段がなく、受けた時点で不正利用の中継になりえます。
3. **Worker は1本のキーを前提にしています。** 複数のキーを扱うには、ローテーション、キーごとの消費の追跡、失効の処理が要り、この規模で持つ複雑さに見合いません。
4. **同じ効果が安全な形ですでにあります。** 提供を考える人が設定で自分のキーを使えば、その人の利用は原資から出ず、その分の枠がそのまま他の人に残ります。

### もし将来受けるなら

方針を変える場合の最低条件です。どれか1つでも欠けるなら受けないでください。

- **提供者が、このアプリ専用に新しく発行したキー**であること（他の用途と共用しない）。
- **提供者の側で、使用額のハード上限を設定済み**であること（OpenAI の usage limits、Anthropic の spend limits など）。上限額を運営者も把握しておく。
- **受け渡しは秘密を扱える経路だけ**で行う。ご意見フォーム・メール・チャット・Issue では受け取らない。フォームにキーらしき文字列が届いたら、使わずに提供者へ失効を依頼する。
- 提供者がいつでもキーを失効できること、失効されても運営者は責任を負わないことを、事前に文面で合意しておく。
- Worker 側は、キーごとに `LIMIT_GLOBAL` 相当の上限を持ち、どのキーでどれだけ使ったかを提供者に報告できるようにしてから受ける。

## 導線の置き方

- **全体の上限（global）に達したときだけ**、「全体の上限は運営者が出せる額で決まっています ▶」を出します（`FreeTierFullNote`, `ErrorText` の `quota-global`）。
- **端末ごと・IPごとの上限に達したときは、お金の話をしません。** それはその人自身の1日の分で、支援があっても増えないからです。ここで寄付を案内すると、支払えば続けられるかのように読めてしまいます。
- 探究の途中、ホーム、バナー、モーダルには出しません。
- リンクが1つも設定されていないデプロイでは、どの導線も出ません（`hasSupportLinks()`）。支援のページ（`#/support`）自体は開けますが、仕組みの説明と「自分のキーで使う」案内だけになります。

## 透明性

支援のページには、手で更新する「残高」は出しません。更新を忘れた数字は、出さないより悪いからです。
代わりに、設定からそのまま出せる事実だけを出します。

- 1日の費用の上限（Worker の `/quota` の `rules.dailyBudgetUsd`。`DAILY_BUDGET_USD` の値で、Worker は実際にこの額で呼び出しを止める）
- 今日の全体の上限と残り（`/quota` の `global`）
- 探究1つの平均費用（`src/lib/support.ts` の `COST_PER_INQUIRY_USD`）。上限額が何探究分かの目安として添える

`rules.dailyBudgetUsd` を返さない古い Worker のときだけ、`COST_PER_INQUIRY_USD` × 全体の上限で1日の額を見積もり、「およそ」と書きます。
`COST_PER_INQUIRY_USD` は `LIMIT_GLOBAL` を決めたのと同じ数字です。モデルや価格を変えて決め直したときは、ここも一緒に直してください。

## 運営者の設定手順

1. GitHub Sponsors のプロフィールを作る（本人確認、振込先、税務情報）。URL は `https://github.com/sponsors/<ユーザー名>`。
2. Ko-fi のページを作り、Stripe か PayPal をつなぐ。URL は `https://ko-fi.com/<名前>`。
3. GitHub リポジトリの Settings → Secrets and variables → Actions → Variables に `SUPPORT_GITHUB` と `SUPPORT_KOFI` を登録する（片方だけでもよい）。
4. 「Deploy to GitHub Pages」を再実行する。
5. 支援が集まって上限を上げるときは、`LIMIT_GLOBAL` と `worker/wrangler.toml` のコメントの計算を直し、「Deploy shared-key proxy」を実行する。
